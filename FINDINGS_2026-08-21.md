## 14.6 THE MAC PORT: FULL RESOLUTION (2026-08-21 ~10:00-12:45, fresh session)

The prior session's "chive" was left unsolved with a START-FRESH directive. A
new session, told to ignore that handoff and do a top-down analysis, resolved
the ENTIRE chain: graphics chive -> server startup -> Marionberry (no server)
-> Turkey (guid mismatch) -> Centipede (crypto handshake) -> full parity with
the PC rig, subclass/ability data included. Six real, distinct root causes,
each verified from actual evidence (wine debug traces + the client/server's
own application-level log files, `Sunrise/logs/sunrise.log`, THE decisive tool
this whole arc - `file_sink` was off and levels were `warn`; turning on
`file_sink=true` + `debug` levels on both client and server settings.json was
the single highest-leverage config change of the day).

**FIX 1 - the graphics chive itself**: not a wine/Metal bug. The manual launch
script's hand-assembled Wine environment was missing ~15 env vars Whisky's own
launcher sets (WINEMSYNC instead of just WINEESYNC, several
WINE_MACH_PORT_*/WINE_DISABLE_NTDLL_THREAD_REGS Darwin-specific tuning vars)
plus a per-app DllOverrides registry entry (`winemetal=b`, `d3d10core=n,b`)
Whisky auto-applies that the script never replicated. Fix = stop hand-rolling
the client's Wine invocation; drive it through a dedicated Whisky bottle
(`whisky create Sunrise`; `WhiskyCmd run Sunrise <exe> --command` prints the
exact working env). GPTK cask wine-7.7 remains the server's engine (unrelated
process, no shared Wine requirement with the client at all - only TCP ports
need to agree).

**FIX 2 - server wouldn't start at all**: `state.db-wal`/`state.db-shm` were
root-owned (leftover from an earlier sudo-elevated port-443 run); a normal-user
process can't write them, so SQLite bailed with "attempt to write a readonly
database" before any logging existed. Fix = delete the two sidecar files
(directory-owner has delete permission regardless of file ownership; the main
`state.db` was untouched). A second, unrelated config bug found the same pass:
`packages_dir` in the server's settings.json pointed at the old
`~/Downloads/depots/...` tree, which had been emptied when the project moved
to `~/Documents/opencode/sunrise-fork/` (Game/, RE_build/, and the Steam depot
copy all moved at some point without every settings.json getting updated -
this exact "docs/settings say path A, disk has path B" pattern recurred
constantly this session; disk is always the source of truth here).

**FIX 3 - Marionberry (no server reachable)**: table stakes - once 1+2 were
fixed the client could actually reach 127.0.0.1:8443, which it couldn't
before.

**FIX 4 - client ran but "base Sunrise", no fork features**: `route_descriptor`
in `client/hooks/network/http/http_descriptor_route.cpp` forwarded every HTTP
descriptor externally whenever `external_server.enabled` was true, without
ever trying the in-process consumer (`http::consume`, which already handles
`/SignOn` and is registered unconditionally by `server::initialize()`
regardless of mode). Removed that branch entirely - the hook now always tries
the in-process consumer first, falling back to 200-empty for anything it
doesn't recognize (the SignOn-sourced content GETs). This is Phase 3 of the
lane-macos-external-hybrid brief, closing what Phase 2 (the config-manifest
GET, already fixed by a prior session) started.

**FIX 5 (two sub-bugs, same session) - server received the client's traffic
but the client never got real data**:
  (a) `server::initialize()`'s non-standalone branch unconditionally called
      `transport::initialize()`/`gameplay::initialize()` (binding the
      client's OWN local BAP/gameplay listener on the SAME port the real
      standalone server uses), on the documented-but-wrong assumption that a
      second bind would simply fail if the port were already owned. On this
      Mac it didn't fail - it silently succeeded (observed: two processes
      both holding LISTEN on :30975), and the client's own gameplay-connect
      call self-satisfied via its own listener instead of ever reaching the
      external server. Fix = gate both calls (and their shutdown) behind
      `!client::hooks::external_server::enabled()`.
  (b) `content_config_get_replacement.cpp`'s `is_manifest_url()` (the routing
      check) correctly recognized both the local marker AND the configured
      external `config_url`, but the actual encode gate right below it still
      used the narrower `is_local_url()` (embedded-marker only) - so a hybrid-
      mode fetch got routed in-process correctly, then fell through to the
      empty-success arm instead of the real manifest (`route=unmapped
      length=30`, exactly the configured URL's length). Fix = use
      `is_manifest_url()` for the encode gate too; `is_local_url` deleted as
      dead code.

**FIX 6 - Turkey (content manifest is invalid: guid mismatch)**: the client
and server both had a stale hand-typed `config_guid` ("09d54b23-...") from an
earlier session. `validate_served_guid()` only validates/logs a configured
override - it never gets injected into what the manifest route actually
encodes (that always uses `state::content_manifest`'s own independently-
computed guid). Cleared the server's override to force it to log its REAL
computed guid ("4979636d-051d-8c5e-b7d1-0f79fdf4abcb", a totally different
value) and set that on the client. The override mechanism is one-way
(validate only); anyone who sets it must independently confirm it matches the
actual computed value or clear it and read the real one from the log.

**FIX 7 - Centipede (BAP secure-channel handshake, "Received unreadable hello
response")**: the deepest fix. `middleware/secure_channel/envelope.cpp`'s
`encode_server_hello` encrypts `bap.nonce`+`bap.sessionKey` (AES-CBC) and MACs
the envelope (HMAC-SHA256) using `signOn.encryptionKey`/`authenticationKey`.
Both were `BCryptGenRandom`'d independently by client and server (two separate
processes, no live handshake of their own in hybrid mode) - two unrelated
random values can never decrypt each other's output. Fix = derive ONLY these
two wrap keys deterministically via HMAC-SHA256(bootstrap_token, label) with
domain-separated labels (`state/runtime/state_runtime.cpp`,
`derive_envelope_wrap_keys`); `bap.nonce`/`bap.sessionKey`/`bap.envelopeIv`
stay genuinely `BCryptGenRandom`'d per boot (the client LEARNS them by
successfully decrypting the hello - only the wrap keys need to be shared in
advance). bootstrap_token is already configured identically on both sides.

**THE STANDALONE SERVER CROSS-COMPILE (net-new Mac tooling)**: fix 7 lives in
shared code compiled into BOTH the client DLL and the standalone server exe -
but the exe running all session was a pre-built Windows/MSVC binary with NO
Mac (MinGW) build path. Stood up a new `sunrise-server` CMake target from
scratch in `RE_build/Sunrise-fork-inventory/Sunrise/CMakeLists.txt`: started
from `sunrise-server.vcxproj`'s file list (stale - missing ~15 files added to
the inventory tree since that snapshot), converged on "the client DLL's full
565-file list minus src/client/**, src/core/ui/**, src/core/runtime/**,
src/server/ui/**, src/steam/**, vendor/detours, vendor/imgui, plus ~15
server-exclusive files (https_listener/tls/persistence/*_test/server_main/
discovery_listener/admin_http/sqlite3.c)" as the reliable method (the client
DLL already compiles the FULL embedded server - proven working - so it is the
authoritative file-membership oracle, not the vcxproj snapshot). Needed
`project(... LANGUAGES CXX C RC)` (C, not just CXX, for sqlite3.c - silently
uncompiled otherwise, zero warning). Hit a stack overflow on first successful
link: the client DLL's `State initialized{}` (large stack struct in
`state::initialize()`) rides on destiny2.exe's own generous host-process
stack when loaded as a DLL; the standalone exe has only its own linker-default
reserve. Fix = `-Wl,--stack,8388608` on the sunrise-server target only.

**THE BUILD-IDENTITY RESTAMP (expected, not a new bug)**: rebuilding the
server exe changed its own PE timestamp+size, which
`RE_output/s1_accept/Sunrise/cache/build_data.bin`'s stored identity header
(`#pragma pack(push,1)` Header struct, `cache/records/format.h`) correctly
flagged as stale (`ev=build_data stage=identity result=mismatch`) - and unlike
content_manifest, build_data has no live rescan-and-rebuild fallback, so it
hard-failed content_swap. `cache_identity_patch.cpp`'s `restamp_equipment_hash`
was the WRONG tool (patches only the eq-hash at fixed offset 20, explicitly
assumes ts/size are stable). Patched offsets 12 (imageTimestamp, u32 LE) and

straight from the server's own "expected_ts"/"expected_size" log fields.
Rule for next time: any server exe rebuild needs this same two-field patch
(or a proper rebuild-aware restamp tool, not yet written) before its next
boot, using ITS OWN freshly-logged expected_ts/expected_size.

**THE PRE-EXISTING, UNRELATED WARNING**: `cached_eq` vs `expected_eq` in the
build_data identity check still differs and always has (present in the very
first successful boot of the whole session, before any of today's fixes) -
this is the OTHER, unrelated "eqHash" mechanism
(`configured_equipment_identity.cpp`, tied to account gear/abilities, not the

"identity mismatch" mechanisms again - build_data (ts/size/eq, PE-identity,

non-fatal) are different systems that happen to share a log-line shape.
