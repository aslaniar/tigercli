### The bucket arithmetic bug (route 2) - verified against the real bytes

Disassembled FUN_1404c1930 fresh from the local unpacked PE
(`RE_scripts/disasm_fn.py`, capstone):

```
sar   esi, 0xd        ; hi = (int32)KEY >> 13 - sign-fill comes from the KEY's bit 31
movzx eax, si         ; (uint16)hi
mov   ecx, esi        ; rcx = ZERO-extended hi (32-bit pattern)
or    rcx, 0xffc0000
shr   rcx, 0x12       ; logical
and   rcx, rax        ; bucket
```

`schema_walk.py`'s `bucket_of()` tested bit 31 AFTER its own logical shift and
then subtracted `1<<32`. That sign-checks the wrong value: x86 `sar` fills from
bit 31 of the ORIGINAL key. For any key with bit31 set the two disagree
completely. Smoke test (`old vs new`):

```
key 0x80806ac0  old-> bucket 3     new-> bucket 9219
key 0x80808635  old-> bucket 4     new-> bucket 9220
key 0x00000123  old-> bucket 0     new-> bucket 0    (low keys unaffected)
```

**Both candidate keys ever probed have bit31 set.** Every "node absent" they
produced was measured in the wrong bucket. Fixed in `bucket_of()`
(`hi |= 0xFFFFE000` when the KEY's sign bit is set).

### The second, deeper finding: those values are not packed keys

For any key whose bit31 is clear, `(hi | 0xFFC0000) >> 18 & (uint16)hi`
reduces to exactly **bits 13..23 of the key** - so the packing is

```
packed_key = (bucket << 13) | index      bucket <= 0x3FF, index <= 0x1FFF
```

and a well-formed packed key never has bit31 set. `0x80806AC0` therefore is not
a resolvable key AT ALL; it belongs to some other identifier space (a hash).
Route 1's hypothesis ("a schema hash may not BE a packed key") is confirmed by
arithmetic alone. Note `0x80806AC0 & 0x1FFFFFF` decodes to bucket 3 / idx
0xAC0 - which is precisely where the OLD buggy math looked and failed. The old
null result was overdetermined: wrong arithmetic AND wrong key domain.

### Consequence: --find needs no key, so neither does calibration

`--find` enumerates `(bucket, idx)` slots directly via `node_at()` and never
touches `bucket_of()`. Since the packing is now known, any hit yields its own
packed key `(bucket << 13) | idx` - `--find` now prints it per match.

**The recursive-expansion fix to `expand()` was landed after the last recorded
`--find 29968` run and that search has never been re-run.** Re-running it
against dump_healthy_inproc.dmp is now the cheapest calibration path and needs
no live capture. If the fully-expanded type-12 total (29,968 bits) matches a
node, we hold the key AND the layout, offline.
