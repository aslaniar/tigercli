### WHY THAT ANSWER CANNOT WORK
The raw hex of a published descriptor decodes as ASCII `steamid:765611987767538..`.
That is foreign-blob truth (20.90's rule: only machineId + offset hex + raw dumps
are facts about a client; every `asif_` field is our layout guessed onto their
bytes, and `routable=0` on a client blob is NOT a claim - do not cite it).
So the client publishes a STEAM-IDENTITY join descriptor, structurally unlike the
IP-endpoint descriptor `descriptor::build` produces. Handing client A that blob
points A at B over Steam networking - which our shim stubs and which never runs:
`get_certificate` returned 0 once and `send_rendezvous` has never fired (20.111).
We answered the search with an address to a road that does not exist.
Note also the RACE: the FIRST client to search always gets `result=none self=1`,
because no foreign advertisement exists yet. Peer-relay answering is order-dependent
by construction.

### THE MEMBER WALK (fn 0x141779230 / 0x141779710, read in full)
    r8d = [container + 0x30]         ; 32-bit occupancy bitmask
    base = container + 8             ; member array, STRIDE 0x120, 32 slots

CONVERGENCE WORTH NOTING: the handbook digest's member ladder, from a wholly
independent source, reads "3 reserved ambassador -> 5 connected -> 7 joined ->
8 waiting -> 9 ready -> 10 established (do not skip edges)". This code enforces
exactly that ladder: it skips 3 and it collects only 10.

### THE FULL CHAIN, TOP TO BOTTOM
For a peer to survive a BAP membership push instead of being thrown out, ALL of
this must already be true, in this order:
  1. the peer occupies a slot in the client's own managed-session member table
     (bitmask at container+0x30, stride 0x120);
  2. its member state at +0x1750 is past 3 (reserved ambassador);
  3. its field at +0x1758 reads 10 (established) - else no record is built;
  4. resolver 0x1404DD640 matches the record's key against a 32-slot, 0x2AC0-stride
     container (occupancy bitmask at +0x5924C, key at entry+8);
  5. fn 0x1404F4980 then inserts the peer into the tracking table
     (client+0x602BC, stride 10) - 20.112;
  6. ONLY THEN does a type-12 membership push naming that peer find tracking data.
Fail any of 1-5 and 20.112's block runs: warn "Could not find tracking data" ->
gate 0x1404F7710 false -> SEND PEER-RESERVATION RELEASE -> set the released latch.

### WHAT THIS SETTLES, AND IT IS THE WHOLE FRONT
**Declaring a peer over BAP can never work by itself.** The activity client does not
take our word for who is present; it reads the game's own session member table and
tracks only members that reached ESTABLISHED. Our type-12 bodies, peer rows, citizen
advertisements and roster pushes are all downstream of a table we have never put
anybody into. 20.110/20.111 measured that table's contents directly on both
machines: `add_candidates` always cnt=1 with the OWN xuid, `poll cand=0` all boot.
The session member table contains self and nothing else, on both machines, always.

That is why twenty boots of wire-shape work produced nothing, and it retires the
whole class: no trailing-field value, no bitmask, no reason byte, and no roster
push can substitute for session membership. It also explains 20.53's freeze lead -
naming a foreign peer in the roster without a reservation - as the same law seen
from the other side.

### AND IT IS EXACTLY WHAT ROAD C BUILDS
The only route to member state 10 is the session/peer layer: connect -> join ->
reserve -> admit -> adoption (20.108/20.109). Our server ALREADY implements the
host side of that ladder: group_host.cpp publishes `MemberState::ready` and
promotes to `established` on join-complete, with three static_asserts pinning the
peer's own bar. What is missing is not code - it is that no client has ever dialed
the gameplay endpoint (L6, zero datagrams, 20.111). Road C was chosen on cost; it
turns out to be the ONLY road. A and B are now formally dead:
  - B (in-process injection at reserve/admit) would have to forge session
    membership AND drive it to established, which is road C with no server.
  - A (peer-native Steam rendezvous) still ends at the same ladder.

### THE RELEASE DECISION, READ END TO END (fn 0x140C17E40 @0x140C18442)
The captured RVA for "Could not find tracking data" IS the return address of that
warning's own log call. What follows it, in ONE basic block:

    0x140C1843D  call 0x14035D860        ; emit "Could not find tracking data..."
    0x140C18442  mov rdx,r14 / mov rcx,r15
    0x140C18448  call 0x1404F7710        ; THE GATE
    0x140C1844F  jne  0x140C185A1        ; gate true -> skip the release entirely
    0x140C1845B  call 0x1404F8250        ; SEND PEER-RESERVATION RELEASE
    0x140C18462  je   0x140C18477        ; release failed -> skip the latch
    0x140C18464  mov r8b,1
    0x140C1846D  call 0x1404FC2E0        ; set the flag TRUE for this peer

The release function 0x1404F8250 does NOT decide anything: its log line sits at its
head (offset 0x1D7 is the funnel return), so it executes a decision made here.
Two call sites total: 0x140C17C0C and this one.

### THE GATE IS A TABLE LOOKUP (fn 0x1404F7710, 85 bytes, read in full)
    count = [client + 0x602B8]
    for i in 0..count:  if [client + 10*i + 0x602BC] == *key: index = i; break
    return (byte)[client + 10*index + 0x602C5]        // entry + 9
Entry stride 10: {u64 key (the peer MACHINE ID), u8 @+8, u8 @+9}. On a MISS index
stays -1 and the read lands on the byte just below the table - a sentinel slot,
not a bug.

### WHO WRITES THAT FLAG (immediate scan on 0x602B8 / 0x602C5, 19 + 5 sites)
- INSERT sites 0x1404F4983 and 0x1404F6FEB: write the key, then set BOTH +8 and +9
  to ZERO, then `inc dword [client+0x602B8]`. A freshly inserted peer therefore
  reads FALSE at the gate.
- THE SETTER is fn 0x1404FC2E0 (`mov byte [rbx+rcx*2+0x602C5], r8b` @0x1404FC330),
  and its ONLY call in this block passes r8b = 1 - immediately after a successful
  release.

### THEREFORE: 20.105 IS CORRECTED, PRECISELY
The +9 byte is a RELEASED-ALREADY LATCH, not a "peer is valid" mark. First
membership update naming an untracked peer: gate false -> release sent -> latch
set. Every later update: gate true -> release skipped, silently. That is exactly
the "self-healing" 20.105 observed - the WARNING stops repeating - but the peer
was released on the first pass and stays released. The warning is not benign at
this site; it is one instruction block upstream of the release.
20.105's underlying claim (the warning sits in a per-peer loop and does not repeat)
stands. Its CONSEQUENCE was read wrong, and boots #10-#13 were read against the
wrong consequence. The release is real and it is the roster's exit door.

### THE QUESTION THIS PROMOTES ABOVE ALL OTHERS
WHY is there no tracking data for the peer? The failing lookup lives higher in fn
0x140C17E40 (2225 B), above the log-line construction. That single lookup decides
whether a peer survives its first membership update. Reading it is the next move
and it costs no boot.

### THE same_region SKIP IS OURS, DELIBERATE, AND NOW ANSWERABLE
20.111 result 5 asked whether `peer_advert result=same_region ... peer_citizen=0`
is a gap. It is not an oversight - activity_membership_push.cpp:183-190 states the
reason: a region record holds ONE descriptor, the local advertisement owns the
record for the local region, and `region_machine_id` keys the host-session row by
region index alone, so a peer advertisement on the same index COLLIDES and retires
the row the local call just built (20.78 defect 3). Skipping makes the collision
unreachable by construction.
Its parked question is: "whose endpoint belongs in a shared bubble" (20.79 gap 5).
ROAD C ANSWERS IT: neither client's - the SERVER's. Both clients are guests of one
host. That is what makes the same-region case resolvable now when it was not in
20.79, and it is the first place road C pays for itself in code we already own.

## 20.62 node+0x14 IS THE PRESENCE BITMAP, NOT THE WIRE WIDTH - AND WITH THAT

### First, correcting 20.61 (mine, one entry old)

20.61 said `node+0x14` "states the wire width outright" and rebuilt `--find` on
it. **Wrong.** Our own type-12 body is 29,968 bits; the largest value at `+0x14`
anywhere in the registry is 8,029, and **92% of all 6,765 nodes read zero there**
- no message width can be zero. A `--find 29968 +/-800` across every live bucket
returns nothing.

What it actually counts, and this reproduces:

```
node+0x14 == sum over fields of (1 if presence else 0)
             + (a nested field's own node+0x14, whether flagged or not)
```

**6,709 of 6,765 nodes match exactly.** It is the size of the schema's PRESENCE
BITMAP, and the per-field dword at `+0x28` is that field's INDEX into it - which

### Bug 1 - the sign fill in `bucket_of` was six bits too wide

20.59 correctly identified that `sar esi,0xd` fills from the KEY's sign bit and

is `0xFFF80000`. 20.59 used `0xFFFFE000`, which fills from bit **13** and so
overwrites bits 18..13 - six real key bits - before the mask is applied:

```

### Bug 2 - the pointer arithmetic never wrapped

```
imul eax, edi                     ; 32-bit multiply
and  rcx, qword ptr [rax + 8]
sub  rax, rcx                     ; 64-bit MODULAR subtract

The stored adjustment at `slot+8` is routinely larger than the slot address, so
the subtract borrows. Python has arbitrary-precision integers and produced a
**negative VA**, which `read_va` reported as "not mapped" - indistinguishable, to
the caller, from an absent node. Every node in every live bucket looked absent
for this reason alone. Both `node_at` and `node_for` now mask to 64 bits, and the
index scale to 32.

### Bug 3 - the field count was reading the message's bit size

`node+0x14` is the schema's TOTAL BIT SIZE (1000 for type-12), not a count.
Walking `count+1 = 1001` records off a 9-record array is what produced the pages
of garbage field rows. `FUN_1404bd2a0`'s prologue gives the real rule:

```
movsxd rdx,[rcx+0x18] ; test edx,edx ; setg al   ; kind flag
mov rax,rdx ; jne .keep ; mov rax,[rcx]          ; limit
```

The loop branches on the same saved flag:

- **flag 0 - STRUCT.** `lea rax,[rbx+rbx*4]` / `[r14+rax*8+0x31]`: one 0x28-byte

- **flag 1 - ARRAY** (branch `0x1404bd525`). ONE element descriptor at a fixed

and yields noise. That is precisely what made `0x808086A9` - a 32-slot member
array - print as "32 garbage fields".
