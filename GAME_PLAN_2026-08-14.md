What makes NOW different from the 08-07 assessment: **the client-side contract is CLOSED.**
Every message the client sends/expects is mapped end-to-end; the server-authoritative
boundary — the 08-07 review's single biggest unknown — is now mechanically enumerable:
any client handler with no client-side data source is server-emitted. That list IS the
server's job description.

## Architecture (the spine)
Sunrise today = in-process server, single player. A full private server needs four layers:
1. **Standalone server process** via the existing `external_server` seam
   (`client.externalServer.{enabled,host,config_url,config_guid}` — the `d2legacy` guid names
   the intent). Lift Sunrise's GPL-3.0 in-process server (BAP listener, SignOn, AES-GCM
   secure channel, families 0/3/4/5 datagen) into its own binary; client hooks stay Sunrise's.
   Unlocks multi-client + real hosting later.
2. **Persistence layer**: DB-backed accounts/characters/inventory (PR #9's file-based
   persistence is the seed; graduate to sqlite).
3. **Content runtime**: replace hardcoded datagen (3 characters, 19 entitlements, fixed flag
   runs) with the extracted .pkg content DB (tiger-pkg + d2-cui-explorer hash methodology).
4. **World sim**: entity slots + bubble authority + spawn sets (recipe fully mapped) → then
   the activity-host reimplementation (combat/AI/missions) — the multi-year wall.

## Phases (dependency order)
- **S0 — Standalone server extraction (weeks).** Fork Sunrise (private); run its server
  out-of-process; client connects via external_server settings; validate against the closed
  client contract (every family has a known client-side landing zone to diff against).
  Deliverable: `sunrise-server` binary + client config; feature-parity with upstream 0.2 +
  PR #9, single player.
- **S1 — Persistence DB + content-driven datagen (weeks–months).** sqlite accounts; datagen
  driven by the extracted content DB instead of hardcoded tables.
- **S2 — Static world population (months).** The spawn recipe (entity-combatants.md R1–R7):
  resolve `0x80809162` spawn sets from .pkg → emit pushes through
  `FUN_1416F17A0 → FUN_1416F1800 → FUN_140E10C10` → idle combatants/NPCs in destinations.
  Vendors slot in here (static defs + storefront opcode). **The old "static-enemy fork"
  milestone = S2.**
- **S3 — Combat substrate (1–2 yr).** Replication schema is client-decodable (position,
  translational_velocity, body_vitality, shield_vitality, damage_sections strings mapped);
  reimplement damage/health/ability rules server-side. No ground truth → approximate.
- **S4 — Missions/strikes scripting (2–3 yr).** Definitions on disk, the engine is not;
  hand-author state machines per activity (AALpy/PM4Py only if traces ever exist).
- **S5+ — Patrol/public events, raids (years).** Approximate; never faithful.
