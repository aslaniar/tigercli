## Thread 1 — Destiny 1 on PC (emulation + private servers)

### Background
- D1 (2014) was never released on PC. It shipped on PS3/PS4/Xbox 360/Xbox One.
  - Note: PS3/Xbox 360 never received the final *Rise of Iron* expansion — emulating the
    PS3 version caps you at base game + The Taken King-era content. (gamerant.com/destiny-1-pc-emulation, 2022-12-27)
- The game is online-only: even the single-player content requires Bungie's servers to boot,
  authenticate, load, and run the mission logic. That's the hard part.

### How it's done [partially INFERRED, see below]
- **RPCS3** (open-source PS3 emulator) runs the PS3 binary of Destiny on a PC.
- **V4NGUARD** is a fan-made *custom server* implementing the D1 server-side protocol.
  The emulated client is redirected to V4NGUARD instead of Bungie's servers.
- This works because D1's client code is fully local (emulated); the network layer just
  needs a compatible peer.
- Status over time:
  - 2022-12: fan "Lucas" demonstrated booting D1 on PC via RPCS3 + V4NGUARD and loading
    into the old Tower. Hitching/stutter, unreliable. (gamerant.com/destiny-1-pc-emulation)
  - V4NGUARD public alpha was promised ~early 2023.
  - 2026-06: YouTube guides claim smooth 60 FPS "RPCS3 emulation + V4NGUARD private servers"
    (youtube.com/watch?v=V6AMxDR3M6E, 2026-06-15). I have NOT verified actual current FPS
    or feature completeness myself.

### The projects & people
| Project | Who | What |
|---|---|---|
| V4NGUARD servers | cohae (github.com/cohaereo) | Custom D1 servers, "fun and preservation", solo project since 2022 |
| V4NGUARD org (github.com/v4nguard) | cohae, nblockbuster, devHazz | Tooling (all Rust): tiger-pkg, quicktag, tiger-parse, swizzleinator, destinypkgtool (archived) |
| V4NGUARD Discord | ~7,716 members | "Destiny 1/2 Reverse engineering/research team" — main hub |

- cohae: "Graphics engineer, technical artist & reverse engineer", Rust/C#/HLSL/C++/Python,
  works on V4NGUARD + Alkahest (D2 asset multitool with a renderer recreation).
- **tiger-pkg** is the key format library: parses Destiny 1/2 `.pkg` files ("Tiger" packages),
  MIT-licensed. Requires **Oodle** (`oo2core`) for decompression. Supports D1 alpha, TTK, RoI,
  D2 beta, D2 pre-BL, D2 post-BL, and Marathon. (github.com/v4nguard/tiger-pkg)
- **quicktag**: "Destiny 1/2 package file data structure explorer" — the reverse-engineering
  workbench for mapping unknown file structures. (github.com/v4nguard/quicktag)

### How to run D1 on PC today (steps, from community guides)
1. Obtain a PS3 Destiny game image (user provides; not distributed).
2. Run it in RPCS3 with a D1-specific compatibility patch.
   - RPCS3 issue #11744 is a feature request for a Destiny patch enabling custom servers;
     the private-server groups use such patches. (github.com/RPCS3/rpcs3/issues/11744)
3. Configure the client to point at V4NGUARD instead of Bungie (DNS/host or patch).
4. Log in via the V4NGUARD auth.

### How it works [VERIFIED mechanism via released source + README]
- It's a **client-side injection mod** (Microsoft Detours hooking) on the old Season of

### 🔬 DEEP-DIVE (2026-08-07, `deep` / V4 Pro — read the actual source)
**The headline finding: Sunrise is NOT "a Detours hook mod" — it is a complete in-process
reimplementation of Bungie's backend for offline play, including the layer V4NGUARD keeps
closed-source (BAP + activity host).** The README's "not a custom server" is true only in
the narrow sense that it's not a *networked* server. ~891 files / 77k LOC. BAP = **Bungie
Activity Protocol** — the exact "activity host" protocol cohae called "too complex to
onboard people into." One person (stanuwu, AI-assisted) reimplemented a working chunk of it
open-source.

Architecture (all KNOWN from source):
- **Injection:** ships as a replacement `steam_api64.dll` (exports full Steam API surface,
  backed by an in-process Steam shim) — the game thinks it's Steam, it's actually Sunrise.
- **Egress guard = the "100% offline" guarantee:** DNS/resolver/winsock all forced to
  loopback; Demonware NAT probe answered locally on ports 3074/3075 with the real XOR masks
  (`0x76C3F6BC` addr / `0xF6BC` port) — direct Demonware-lineage RE.
- **16 byte-signature-scanned Detours hooks** (wildcarded, no hardcoded offsets):
  transport_kind (forces socket over SDR), http_execute_request (intercepts every HTTP
  descriptor → in-process server), signon readiness force-pass, content manifest gate
  (signature-verification bypass), queuez, spawn gate, retail log, Steam auth fakes.
- **In-process server:** loopback TCP on port 30974; plaintext channel start → AES-GCM
  encrypted channel; ~25 BAP service IDs routed (activityHostManager, activityMessage,
  webService, subscribeFamily, matchmaking, signSteamCertificate, accountFromMembership...).
- **Activity-host protocol (svc 8):** ~40 message types — join/entity-slot leases (8192-slot
  bitmap), authority (abandon/abdicate/purge/host-query), membership, incident, patch epoch,
  entity state, + 14 accepted-but-ignored named messages.
- **Spawn gate reverse-engineered:** 7 predicates (G1–G7: world present → slice-set →
  participation record (760-byte type-13) → activity lifetime → world-controller → team
  block → spawn-suppressed), each probed at its call target for diagnosis.
- **Destination selection:** svc-6 selection protobuf (package name, arrival bubble hash,
  spawn-set hash, element index) → 137-byte svc-7 activity session; authored arrival
  overrides in settings (e.g. `raid_gluttony_0..5 → bubble 2, spawn 0x8029E4B4`).
- **Hardcoded vs runtime:** hardcoded = character identity, FNV loadout hashes, entitlements,
  unlock tables, signon identity; **read from the user's own build at runtime** = content
  token, all packages/tables/tags/names. "No copyrighted data" held rigorously.

Already RE'd: BAP transport + AES-GCM, full signon protobuf (fields 1–14), account

### Steam depots & manifests — how users obtain the old build (mechanics)
- Steam content is split into **depots**; each depot has **manifests** = a snapshot of the
  file list (names + hashes + sizes) for one exact build, identified by a manifest ID.
  Steam normally serves only the latest manifest, but `steamcmd download_depot
  <appid> <depotid> <manifest_id>` fetches any manifest you have access to.
- stanuwu lists depots 1085661/1085662 + manifest IDs in his README so users can pull the
  exact **Season of Arrivals** build from Steam's CDN, even though the live game has long
  since moved on. This is the "version pin" that makes the tool reproducible for everyone.
- Why it matters to the endeavor: (a) the vaulted content only exists in the old build;
  (b) the tool is pinned to one build (86657 per d2-cui-explorer); (c) it keeps the project
  legal — no game data is distributed, users fetch a build they own via a Valve-provided
  mechanism; (d) it generalizes: *any* D2 build still on the CDN can be archived this way,
  which is the answer to "Bungie's lawyers had to use fan YouTube videos" (see Background).
- Caveats: D1 was never on Steam, so manifests don't help D1 (console discs/dumps only).
  And manifests can be retired by Valve — archiving while fetchable is the preservation play.

## The technical landscape — how game-server RE works here (for the newcomer)

Four distinct layers, and each has its own community/effort:

1. **Asset/format RE** — the `.pkg` (Tiger) format, Oodle compression, tag/entry structures.
   This is mostly solved and tooled (tiger-pkg, quicktag). It's how people extract maps,
   textures, and know what exists on disk.
2. **Client-side modding/hooking** — patching the client binary to skip auth, enable
   noclip/fly, load arbitrary maps. This is what stanuwu's tool does. Requires finding
   functions in the binary (Ghidra/IDA), knowing the engine's "activity/slice/bubble/spawn"
   loading concepts.
3. **Network protocol RE** — capturing and documenting the client↔server wire protocol
   (Wireshark/mitmproxy). [Deep review correction: this is its own discipline and the actual
   bottleneck for server emulation — see Deep review section above.] Servers are live as of
   2026-08-07, so this is NOT time-limited, but it is the most unclaimed, highest-value niche.
4. **Server-side emulation** — reimplementing the online protocol so an unmodified (or
   lightly patched) client can play against a fan server. This is V4NGUARD's work for D1.

## Reference: D1 architecture & the emulation gap (educational summary, 2026-08-07)

Synthesis written for a CS-background newcomer. Separates VERIFIED from INFERRED. This is
the "state of the art explained" doc — worth reading before any future contribution work.

### The three-layer architecture [INFERRED shape, verified facts inside]
D1 runs on Bungie's **Tiger engine** (same family as D2 and Marathon). Online-only on all
platforms. The server side is not one thing — three distinct domains:

| Layer | What it is | Status |
|---|---|---|
| **Client** (binary on console) | Rendering, physics, input, UI, local state | Fully obtainable (disc dumps), runs under RPCS3 |
| **Backend services** | Accounts, characters, inventory, quests, vendors, social spaces | Partially reimplemented (V4NGUARD auth/social; kallsyms persistence) |
| **Activity/world services** | Mission logic, enemy spawning, encounter scripts, matchmaking, instancing | **The real gap — unbuilt publicly** |

### How emulation was achieved (step by step)
1. **RPCS3 emulates the PS3** (PPC→x86, PS3 OS, RSX GPU). RPCS3 now boots every PS3 game,
   so the D1 binary runs. The emulator cannot conjure Bungie's servers, and the client
   won't boot without them.
2. **Fan servers reimplement the protocol**: DNS redirect + auth + message handling.
   V4NGUARD got the client into the Tower (2022). kallsyms went further into persistence
   (char creation, inventory, quests — 2026).
3. **The protocol** was derived from (a) hooking the client binary to read what it sends/
   expects, and (b) packet capture on live traffic. D1's backend ran on Activision's
   **Demonware** middleware (same lineage as CoD) — hence `dev-stun.demonware.net` and why
   the open-source Demonware reimplementations are directly relevant.

### What's missing & how to obtain it (ranked by leverage)
1. **Live protocol capture** — run D1 on real hardware/RPCS3 against Bungie's real servers,
   intercept + decrypt (Wireshark/mitmproxy + crypto hooking in client), document message
   formats — *especially activity/matchmaking*. Servers are live (2026-08-07, active
   playerbase) — valuable but not deadline-driven.
   `demonware-companion` (deserializer/interceptor) is a ready-made template. → **#1 gap-filler.**
2. **Ghidra the PS3 binary** — the client *is* the protocol spec: every message it sends and
   expects is encoded in its functions. Offline, never expires. The skill floor for real work.
3. **Sibling ecosystems** — open-bitdemon-emulator (auth/crypto/lobby skeleton),
   Project Cartographer / ElDewrito (Bungie-adjacent matchmaking+persistence), OpenMU
   (full MMO server organization), Transformers-Demonware-Server (dead Activision game).
4. **XenonRecomp detour** — recompile the X360 build to native C++, redirect network calls
   at the C++ level via PPC_FUNC hooks (may beat fragile emulator patching). Unproven on D1.

### The fundamental principle (from user's CarPlay analogy)
- The **client is fully decodable** — exactly like scraping the car's OS. Ghidra on the D1
  binary ≈ Ghidra on the head unit's libAirPlay.so. Half the spec is yours forever.
- The **authoritative server is NOT obtainable** — no disc, no dump, no leak. Unlike the car
  (self-contained; the "server" was in the same firmware), D1's authority lives in Bungie's
  private cloud. You can decode the *protocol* (client expectations + wire captures +
  Demonware lineage) but the *gameplay logic* (spawn/AI/encounter/loot decisions) can only
  be reconstructed, never extracted.
- **Consequence:** "decode exactly what's needed" works for the protocol; real D1 gameplay is
  inherently a "reimplement and approximate" problem.
- Bonus: **internal/dev builds** (e.g. moji_irl's Dec 2013 pre-alpha) sometimes carry more
  client-side logic, debug endpoints, or test-server configs than retail — extra spec source.

## Automation architecture — rebuilding the Bungie backend (from `/deep` expansion, 2026-08-07)

Goal: systematically discover D1's game systems and reconstruct the server, rather than
per-activity manual RE. Deep's design, verified inputs, ranked next actions. The Bungie
backend splits into three layers: **static config** (items/activities/vendors/spawns — ~30-50%
known), **dynamic logic** (encounters/scripts/AI — ~5-10% known), **infrastructure**
(auth/session/persistence/Demonware — ~40-60% known).

### The five-tool pipeline

| Tool | What it automates | Inputs | Feasibility |
|---|---|---|---|
| **1. destiny-manifest-extractor** | Extract ALL declarative game data (activities, items, vendors, quests, destinations, spawns) into a structured DB | .pkg (via tiger-pkg), Bungie.net D2 API (format knowledge; some D2 content is reissued D1), archived D1 DBs (destinysets.com, light.gg, DIM), stanuwu's hash-resolution methodology | HIGH — can start TODAY, no expiry |
| **2. destiny-protocol-recorder** | Record full gameplay sessions: timestamped client↔server messages + synchronized game state (video + state snapshots) | Real console/RPCS3 on LIVE Bungie servers, demonware-companion data_interceptor, crypto keys from Ghidra | HIGH for soloable content; NOT urgent (servers live as of 2026-08-07) |
| **3. destiny-handler-mapper** | Ghidra/IDA scripting → find every network message handler + payload field layout → machine-readable message schema (JSON) | D1 PS3 EBOOT / X360 XEX | MEDIUM-HIGH — unblocks Tool 2 |
| **4. destiny-state-inference** | From multi-run recordings + schema: infer each activity's state machine (deterministic vs conditional messages, trigger conditions) | Tool 2+3 output; process-mining/automata-learning methods | MEDIUM — invisible server counters/RNG seeds limit completeness |
| **5. destiny-server-generator** | Generate a Rust server: Demonware layer (adapted from open-bitdemon-emulator) + persistence (kallsyms layer) + activity engine replaying inferred state machines + social spaces | Tools 1-4 + open-bitdemon-emulator | MEDIUM for playable skeleton (strikes/story/patrol); never 100% accurate (RNG, anti-cheat, removed content) |

### Dependency order & critical path
1. Static config extraction (Tool 1) — start today, no deps, no expiry.
2. Client handler mapping (Tool 3) — start today, no deps (Ghidra + binary).
3. Live protocol capture (Tool 2) — **must start now**; depends on Tool 3 to know what to
   look for + crypto keys.
4. State inference (Tool 4) — depends on 2+3.
5. Server generation (Tool 5) — depends on 1-4.
Critical path: **3 → 2 → 4**. Tool 1 parallel.

### XenonRecomp's role (the accelerant)
If XenonRecomp compiles D1's X360 binary (never attempted), Tools 2-4 get dramatically
easier: the recompiled client is readable C++; send/receive functions can be *replaced* at
source level — full payload logging, encryption bypass, injected responses, no crypto-key
extraction, and recorded-response replay for testing state-machine hypotheses. UNVERIFIED
whether it compiles D1 without modification — that is the highest-upside, lowest-cost
experiment.

### What CANNOT be automated (fundamental limits)
- Server logic with no observable client effect (metrics, A/B gating)
- Content never played publicly (cut content, internal test activities)
- Exact reproduction — behavior yes, code no.

1. **Verify D1 API data availability** — is https://www.bungie.net/Platform/Destiny/Manifest/
   still live? Do destinysets.com / light.gg / DIM archive D1 manifests? Determines how much

## Automation breakthrough — breaking the verification-oracle bottleneck (2026-08-07, `@general`)

Two independent `general` runs (automation-bypass + verification-oracle) converged on the
same answer: **the circularity is a framing error.** The client itself is the oracle — you do
NOT need Bungie's servers to get runtime ground truth.

### New verified infrastructure (this session)
- **RPCS3 has a built-in GDB server** (enabled by default; commits a29d4150, 6b1e1e40,
  a2d5b5a0) — scriptable breakpoints + memory access to the emulated PPU. No Frida needed.
- **RPCS3's `sys_net.cpp` is a single chokepoint** (1,893 lines, all ~110 PS3 socket
  syscalls with existing logging hooks) — every byte of D1 network traffic passes through
  one open-source file. Patching it for traffic logging is days, not a research project.
- **RPCS3 savestates** (`savestate_utils.cpp`) + **headless/CLI mode** (active Apr-Jun 2026).
- **angr supports ppc32/ppc64** (the PS3 PPE; no SPU backend).
- **D1-era manifest archives exist on GitHub** (fallback if the API key check fails):
  `nmlorg/destiny-db` (128 MB, 2016, revision history), `dad2cl3/destiny-manifest-manager`,
  `lowlines/destiny-manifest-extras`.
- Protocol-inference literature: **POLYGLOT (NDSS'20)**, Netzob, gisele — all infer message
  formats *without ground truth* by treating the responsive peer as the oracle.

### Why the circularity is breakable (3 reasons)
1. **A reactive peer suffices, not a complete server.** V4NGUARD (Tower) and kallsyms
   (char/inventory/quests) already ran the loop by hand: decode N messages → stub answers N
   → client advances → new traffic appears. Each decoded message extends the capture horizon.
2. **Client-originated traffic bootstraps with zero protocol knowledge.** DNS-blackhole the
   endpoints, run a log-only listener: the client emits its handshake/auth requests
   unprompted. Those first blobs decode with publicly documented Demonware auth knowledge.
3. **The client contains both encoder and decoder for every message.** Client→server captures
   are ground truth for those formats (round-trip check, offline).

### The six mechanisms, ranked
| # | Mechanism | Role | Feasibility |
|---|---|---|---|
| 1 | **Reactive-client harness** — instrumented RPCS3 (sys_net logging + savestates + GDB) + stub peer; client advancement = verifier | THE missing oracle | HIGH |
| 2 | **Value-space matching** — manifest + .pkg asset-hash universes as field labeler (unique-domain hit = "this is itemHash") | Persistence-layer labeler | HIGH |
| 3 | **Corpus parser verifier** — codegen agent schemas into Kaitai Struct parsers; mechanical reject gates (exact byte consumption, stable alignment, hash resolution) | The "compiler" the agent lacks | HIGH |
| 4 | **Assert/log-string mining** across retail + pre-alpha builds | Seeds everything else | HIGH (hours) |
| 5 | **Live D1 API** as independent persistence witness (if key-check passes) | Second witness | UNVERIFIED (data-serving unknown) |
| 6 | **Demonware framing wedge** (open-bitdemon-emulator) | Bootstrap layer | MEDIUM (version-match UNVERIFIED) |

### Bootstrap order
`#4 string mining (hours) → locate send/recv + Demonware funcs → #1 sys_net logging (days) →
capture client-originated handshake → #6 framing peel → #2 hash universes in parallel →
#3 corpus verifier gates every agent output → iterate loop.`

### Automation model that actually works
**Human seeds, agent amplifies, harness verifies.** Every schema the agent proposes is
codegen'd to a Kaitai parser and tested against real captured blobs; only runtime-confirmed
layouts graduate to the knowledge graph; unverified ones stay flagged. This kills the
"confident garbage" failure mode because there's a mechanical reject gate (Kaitai parse
failure = schema rejected). The agent is a multiplier on top of the harness, not a
replacement.

### Dead ends confirmed
- **D2→D1 wire-protocol transfer**: the "documented D2 API" is the Bungie.net HTTP/JSON web
  API, NOT the in-game wire protocol. No public D2 wire-format documentation exists.
  Transfer only gives *priors* (Tiger serialization, tag/hash systems, Demonware lineage).
- **Live-server capture as foundation** (stress-test stands).
- **auto-re-agent standalone** — useful only as the handler-body reconstruction stage
  AFTER the harness supplies anchors.

**THE SINGLE MOST PROMISING PATH:** the #1 reactive-client harness — schema-driven stub +
instrumented headless RPCS3 (via its built-in GDB server + sys_net logging), scoring every
protocol hypothesis by whether the client advances. It manufactures the missing verifier
from an artifact you already own, needs zero Bungie servers, uses only verified-to-exist
infrastructure, and is empirically known to converge (V4NGUARD/kallsyms walked it by hand).
